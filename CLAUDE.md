# decoder-game — контекст для Claude Code

Сайт с игровыми комнатами (Node.js/Express/Socket.IO, бэкенд; vanilla JS,
фронтенд). Изначально там жила только игра «Декодер». Сейчас добавлена
вторая игра — **Ticket to Ride (карта Европы)** — через уже готовый
механизм подключаемых игровых модулей. TTR полностью играбельна (бэкенд +
клиент), но билеты — черновой список (см. ниже), а UI не отполирован.

## Архитектура (уже реализована, не менять без причины)

- `server/games/<id>/` — самодостаточный модуль игры (по образцу
  `server/games/decoder/`). Контракт: `id, label, teamKeys, canStart(teamOrder, players),
  startRequirementText, create(players, teamOrder, usedWords), fromData(...)`
  + методы экземпляра для конкретных действий, `viewFor`, `toJSON`,
  `canPlayerLeaveSafely`, `finished/winner/winReason`, `getArchiveSummary`.
- `server/games/index.js` — реестр модулей (`GAME_MODULES`), новая игра
  добавляется туда одной строкой.
- `server/game.js` — `Room`/`RoomManager`, общая оболочка (игроки, лобби,
  чат, персистентность). Ничего не знает о правилах конкретной игры,
  только вызывает общий контракт. `Room._delegate()` — тонкие делегаты в
  `this.game`.
- `server/server.js` — socket-события. Общие (`create-room`, `start-game`,
  `set-game-type`...) уже не требуют правок для новой игры, но
  **специфичные для конкретной игры действия всё равно нужно добавлять
  сюда явно** (по одному `socket.on(...)` на действие) — вопреки
  комментарию в `games/index.js` про "server.js трогать не нужно", это
  верно только для регистрации модуля, не для его действий.
- `server/store.js` — файловое хранилище комнат, полностью общее,
  трогать не нужно.

## Ticket to Ride — что уже сделано

`server/games/ttr/`:
- **`map.js`** — 47 городов + 100 маршрутов карты Европы. Данные
  извлечены из авторского SVG (нарисован в Figma, координаты городов и
  сегментов пришли оттуда же). Каждый маршрут: `from/to/length/color/
  variant/tunnel/ferry`.
- **`rules.js`** — чистые функции: колода (110 карт: 8×12 цветных + 14
  локомотивов), проверка оплаты маршрута, разрешение туннеля (вскрытие 3
  карт + доплата), проверка выполнения билета (BFS по графу владений),
  самый длинный путь (DFS-перебор), таблица очков за длину (1→1 ... 8→21).
- **`tickets.js`** — ⚠️ **ЧЕРНОВИК**, ~20 билетов для обкатки механики.
  Это НЕ полный официальный набор (в игре 46 карточек) — нужно заменить
  на выверенный список, как и с картой (см. ниже про доверие к данным).
- **`index.js`** — класс `TicketToRideGame`: раздача начальных билетов
  (`initial-tickets` фаза, плюс стартовая рука `HAND_SIZE_INITIAL` карт —
  раньше константа была объявлена в `rules.js`, но нигде не вызывалась,
  игроки стартовали с пустой рукой; починено), обычный ход (`playing`),
  финальный круг по вагончикам (`final-round`), подсчёт очков.
  `viewFor()` отдаёт список игроков под ключом `ttrPlayers` — специально
  НЕ `players`, чтобы не перетирать общий `players` (connected/isHost) из
  `Room.viewFor()` при `{...base, ...gameView}` (были на этом баге).

Зарегистрирован в `server/games/index.js`, делегаты добавлены в
`server/game.js` (`drawCard/claimRoute/resolveTunnel/drawTickets/
chooseTickets`), события — в `server/server.js`
(`draw-card/claim-route/resolve-tunnel/draw-tickets/choose-tickets`).
Статика карты (города/маршруты/цвета карт) отдаётся клиенту через
`GET /api/ttr/map` (`server.js`) — без этого клиенту негде взять
`route.length/color/tunnel/ferry` для панели оплаты, в сокет-view их нет.

**Важно про TTR и `teamKeys`**: в этой игре нет команд, `teamKeys: []`.
`Room.canStart()` получает и `teamOrder`, и `players` (правка в `game.js`,
раньше туда передавался только `teamOrder`, и `TicketToRideGame.canStart`
всегда видел 0 игроков) — Декодеру `players` не нужен, TTR он нужен вместо
`teamOrder` (там считается просто число игроков, 2–5).

Лобби (`public/`) для игр без команд (`teamKeys: []`) не рисует блок А/Б —
`renderLobby()` в `app.js` прячет `.teams-grid`, оставляя общий список
игроков (переиспользует `#unassigned-list`) и кнопку «Начать» напрямую.

## Важные фактические решения по данным карты (не путать при доработке)

- Цвет `#AC7F5E` в файлах карты — это **"white"**, а не "purple" (внешне
  выглядит коричневатым/кремовым, так решил автор карты, чтобы не
  сливалось с фоном). Уже учтено в `map.js` (`color: 'white'`).
  Настоящих 8 цветов вагонных карт: `pink, white, blue, yellow, orange,
  black, red, green` (+ `gray` — маршрут принимает любой один цвет).
- `tunnel`/`ferry` в `map.js` определены по структуре самого SVG (не по
  правилам "с нуля") — `tunnel: true`, если все сегменты маршрута лежали
  в группах с именем `tunnel*`; `ferry: N` — по числу декоративных
  иконок-локомотивов внутри группы маршрута (совпадает с минимальным
  числом обязательных карт-локомотивов для оплаты).
- Карта была вручную нарисована в Figma и несколько раз пересобиралась
  из-за проблем с экспортом `id` — если придёт новый экспорт карты,
  логику проверки (уникальность id, привязка городов/маршрутов, цвета,
  длины через подсчёт сегментов) стоит повторить, а не доверять файлу
  вслепую.

## Клиент TTR (`public/`) — что уже сделано

- `public/ttr/ttr-map.svg` — карта из Figma, id совпадают 1:1 с
  `map.js` (`city_<name>`, `route_<city1>_<city2>[_1|_2]`) — сверено при
  подключении, расхождений нет (кроме декоративного дубля `city_kharkov_2`
  в самом SVG, на данные не влияет). Вставляется в `#ttr-map-container`
  через `innerHTML` (не `<img>`), один раз за партию (`mountTtrMap()` в
  `app.js`, вызывается при переходе лобби→игра), а не на каждый рендер —
  это дорогой (~2.4 МБ) DOM, перевставлять на каждый socket-апдейт нельзя.
  Метаданные (города/маршруты/цвета карт) клиент берёт из `GET /api/ttr/map`,
  а не парсит из SVG.
- `#screen-game-ttr` в `index.html` — отдельный экран, `#screen-game`
  остался как был, только под Декодер.
- В `app.js`: делегирование кликов по маршрутам через
  `closest('[id^="route_"]')` на `#ttr-map-container`; слой владения красит
  дочерние `rect/path/polygon/circle` маршрута в **цвет игрока**
  (`TTR_PLAYER_HEX[playerColor]`), не трогая исходную заливку
  (`route.color`) непринятых маршрутов — две разные, не пересекающиеся
  шкалы цвета, как и задумано; наведение/доступность маршрута — через
  CSS-классы `.ttr-claimable`/`.ttr-selected`, не через перекраску. Панель
  оплаты и панель туннеля — общий компонент-степпер (`ttrPaymentTile`) с
  +/- по каждому цвету, максимум ограничен и рукой, и длиной маршрута.
  Билеты (стартовые и добор в свой ход) — один и тот же оверлей-пикер.

**Грабли с `[hidden]`**: несколько раз ловили, что `display: flex/grid`,
поставленный на класс без исключения, перебивает нативный
`[hidden] { display:none }` (одинаковая специфичность, но авторский CSS
всегда бьёт UA-стили). При добавлении новых блоков, которые скрываются
через атрибут `hidden`, а не через JS-класс — не забывать
`.selector[hidden] { display: none; }` рядом с правилом, которое задаёт
`display`.

## Чего всё ещё нет / не доверять вслепую

- **`tickets.js` — по-прежнему черновик** (~20 карточек вместо полных 46
  официальных) — можно играть, но список не выверен.
- Нет автоматических тестов на движок TTR (`rules.js`/`index.js`) — вся
  проверка пока вручную/через Playwright сценарии.
- UI не полирован: нет подсказок «сколько очков даст маршрут», нет
  подсветки городов из билетов на карте, нет мобильной адаптации карты
  отдельно от общей `@media (max-width: 560px)`.

## Общий архитектурный принцип по картам/маршрутам (если будут другие игры с картами)

Геометрия карты — статичный ассет, рисуется один раз в Figma, рантайм
только красит уже существующие элементы по `id`, никогда не пересчитывает
координаты или форму заново.

## Публичный подбор и приватные комнаты

- Room.visibility: `private` по умолчанию (включая старые сохранения), либо `public`.
  У публичной комнаты hostId всегда null; игра выбирается событием `find-game`.
- `RoomManager.findPublicRoom(gameType)` случайно выбирает только ожидающие публичные
  комнаты с местами; minPlayers/maxPlayers объявлены в игровых модулях.
- `Room.updateStartDeadline` и таймеры server.js запускают публичную игру автоматически;
  MATCH_START_DELAY_MS=15000. При нехватке онлайн-игроков отсчёт отменяется.
- Приватный `join-room` всегда требует inviteToken. REQUIRE_INVITE больше не действует.
  Публичный вход доступен только через подбор или восстановление существующего участника.
- Выход разрешён всегда. removePlayer завершает активную игру при окончательном уходе
  участника. Disconnect только помечает игрока офлайн, не удаляет его и не завершает
  партию. DISCONNECT_GRACE_MS удалён из настроек. Несколько вкладок учитываются вместе.
- `/api/games` отдаёт каталог для выбора игры до публичного подбора.
- Тесты: `npm test --prefix server`, включая реальные Socket.IO-подключения.

- `my-rooms` возвращает комнаты только текущей защищённой сессии для кнопки возврата
  на главной. Осознанный выход помечается player.left и исключает комнату из списка.
- `Room.canForceEnd` проверяет завершение при офлайн-участнике: публичная — любой
  участник, приватная — хост, либо другой участник при офлайн-хосте. Проверка на сервере.
  `canManagePrivate` позволяет продолжить приватную комнату после завершения без хоста.

## Codenames

- `server/games/codenames/index.js`: отдельный модуль, 4–8 игроков, команды A/B
  и капитаны назначаются случайно. Словарь переиспользует `decoder/words.js`.
- Поле 25 карточек, фазы clue / guessing / finished. Действия `codenames-clue`,
  `codenames-reveal`, `codenames-end-turn` валидируются в security.js и делегируются
  Room в игру. Капитаны не открывают карточки; агенты не получают секретные типы.
- `viewFor().codenames` содержит персональный вид без изменения общих полей Room.
  Неоткрытые kind=null для агентов и зрителей. После завершения раскрывается всё.
- `public/codenames.js` обслуживает отдельный экран `screen-game-codenames`,
  итоговый отчёт и архив. Подсказки 0 и unlimited допускают неограниченные попытки;
  завершить ход можно после хотя бы одного выбора. Семантика подсказок — на игроках.
- Основные тесты в `server/test/codenames.test.js`.

- Накладки Codenames: PNG в `public/codenames/cards/`, имена сопоставляются в
  `cardImages` (`public/codenames.js`). `renderBoard` сохраняет DOM карточек через
  WeakMap, чтобы чат не перезапускал анимацию и не пересоздавал изображения.
  `newReveals` учитывает номер партии, а не раунда. Итоговый отчёт получает тот
  же ключ партии, чтобы последнее открытие (включая убийцу) тоже анимировалось.
